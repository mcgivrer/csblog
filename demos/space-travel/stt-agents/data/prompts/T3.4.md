TÂCHE T3.4 — Cohérence des états affichés sur les cartes des agents (stt-agents)

PROBLÈME (signalé par le mainteneur). Sur une carte d'agent, la pastille d'état et le badge du lanceur disent « Terminé » (et la tâche est « Fait » au Kanban), mais la barre d'étapes (Brief, Spec, Dév, Revue, Clôture, PR, Livré) reste sur « Dév ». Il faut que tous les états affichés pour un même agent soient cohérents de bout en bout.

CAUSE CONNUE. `Transcript.phase()` (`stt_agents_server.py` ≈ ligne 551) déduit l'étape des seuls rôles vus dans la session ; `Hub.build()` (≈ 990-1005) ne la corrige que via une PR GitHub fusionnée. `withRunStates()` (`index.html` ≈ ligne 576) change l'état affiché (Terminé / Arrêté / Échec) côté client mais pas l'étape. Une tâche lancée par le lanceur a une ligne du plan avec `session` et `runState` (champs réservés RUNNER_RESERVED) : le statut de la tâche (`todo`, `doing`, `review`, `done`…) est la vérité de l'avancement.

À FAIRE
1. Serveur : pour chaque agent dont la session correspond à un run du lanceur (`runner.runs[...].session == id`) ou à une ligne du plan portant ce `session`, ajoute au JSON de l'agent `task` (id de la tâche) et `task_status` (statut de la ligne du plan). Lis le plan SANS lancer Node à chaque cycle : cache invalidé par l'`mtime` de `plan-status.js` (réutilise `read_plan` ; une erreur de lecture ne doit jamais empêcher la construction de l'état : garde l'ancien cache ou aucun `task_status`).
2. Étape (`phase`) cohérente avec l'état : si `task_status == 'done'` → phase 6 (Livré) ; `review` → au moins 3 (Revue) ; sinon inchangé ; une PR fusionnée garde la phase 6 ; ne jamais faire reculer une phase déjà plus avancée. Écris cette règle dans une fonction pure, testable sans serveur.
3. Interface (`index.html`) : la barre d'étapes d'un agent « Terminé » (état affiché `done` via `withRunStates`) dont la tâche est « Fait » montre « Livré » comme étape courante et toutes les précédentes en « fait ». Un agent « Arrêté », « Échec » ou « Tué » ne montre JAMAIS « Livré » : l'étape reste celle atteinte. Affiche le numéro de tâche (`task`) en petit à côté du libellé de l'état si l'agent en a un (chaîne échappée par `esc`).
4. AUDIT « DE BOUT EN BOUT » : liste dans ton rapport, en une matrice courte, chaque endroit où un état d'agent est affiché (pastille `STATE`, libellé `state_label`, badge `rctl` du lanceur, étapes, sous-agents `lifecycle`, filtres et compteurs `GROUP`, tuiles KPI « T'attendent », « En action », ligne d'arbre) pour les états : en cours, attend, validation, en pause, terminé (tâche faite / non faite), arrêté, échec, tué, orphelin, livré (PR fusionnée). Corrige toute incohérence trouvée DANS `demos/space-travel/stt-agents/` (même si elle n'est pas listée ci-dessus) ; signale celles que tu ne corriges pas.
5. Tests : tests unitaires de la fonction de phase (tous les cas de la matrice) ; un test serveur (faux agent + plan de test) montrant que `task`/`task_status` apparaissent et que la phase passe à 6 quand la ligne passe à `done` ; un test d'interface (Playwright, `ignore_default_args=["--hide-scrollbars"]`) montrant la barre « Livré » pour un run terminé dont la tâche est faite, et l'absence de « Livré » pour un run tué. Les tests existants doivent rester verts.
