But : le serveur détecte les événements importants et les publie dans un tampon `notices` envoyé dans /api/state (donc par le flux SSE existant), pour que la page affiche des notifications. Format d'une notice : {id (entier croissant, jamais réutilisé), ts (ISO), kind (identifiant machine, ex. agent_waiting), cat (catégorie parmi `attention`, `agents`, `kanban`, `pr`, `runner`), severity (`info`|`attention`|`error`|`success`), title (court, français), body (une ligne, français, ≤ 140 caractères), target ({type:'agent'|'task'|'pr', id}), key (clé de déduplication)}.

Événements à détecter (diff entre deux instantanés, sans notice sur le PREMIER instantané : base de référence) :
- cat attention : une session passe à l'état waiting (« T'attend ») ou permission (« validation ? »), severity attention ; target agent = id de la carte.
- cat agents : un agent créé (liste `subagents` de chaque session, champ lifecycle) passe à `rapport rendu` (success), `arrêté` (info), `erreur` (error), ou devient `silencieux` (attention, « à arrêter ? ») ; une session passe à Livré.
- cat pr : PR ouverte (info), mergée (success), fermée sans merge (info) — d'après `github.prs` si disponible.
- cat kanban : (via un crochet appelé par le serveur après kanban_apply, avec les changements : id de tâche, ancien et nouveau status) tâche → `review` (attention : « à relire »), → `done` (success), → `blocked` (error), nouvelle tâche créée (info). Pour cela, enrichis le compte rendu de kanban_apply (champ `status` nouveau dans l'entrée `changes` de chaque op `task`) sans changer son comportement.
- cat runner : l'API `NoticeEngine.emit(...)` doit permettre au futur lanceur (T1.4) de publier ses propres notices ; rien à détecter ici.
Anti-bruit : une même `key` n'est pas republiée dans les 30 s ; au plus 200 notices en tampon (anneau) ; /api/state expose les 50 dernières + `notice_seq`.
